# MIG-03: Archive original media and implement asset mapping

## Prerequisites
01 asset contract; fixture development can run alongside 02.

## Ownership boundary
`scripts/import_media/, public/wp-content/, tests/import_media/, migration/assets/`. Work on a dedicated `codex/mig-03` branch/worktree. Do not edit another task's owned files without coordinating. Integrate schema changes through MIG-01 and renderer command changes through MIG-04.

## Work
Archive owned original masters byte-for-byte in Git LFS when appropriate; keep source-repository size below GitHub's recommended 1 GB where feasible. Do not copy every WordPress-generated size into Pages output by default. From the complete available inventory and observed content/layouts, generate/package only required responsive renditions, using Astro's processed image assets (never unprocessed `public/` assets for generated variants). Select a deliberately bounded width set after measuring blog-column, gallery and hero breakpoints against source dimensions; do not hard-code widths before layout evidence exists. Report generated variant counts and bytes and check them in CI. Browsers generally download one suitable `srcset` candidate per image view, but all generated candidates count toward published output. Record original and rendition source URL, destination, MIME, bytes, SHA-256, dimensions, metadata and references. Inventory observed legacy URLs including size-suffixed variants and CDN aliases, and define/test an explicit compatibility policy for unobserved variants rather than inferring they are unused from crawl absence. Cover srcset, CSS backgrounds, posters, alt text, captions, attribution, audio, video and downloads. Preserve embed provider IDs, parameters, aspect ratios and captions. Detect old-host/CDN dependencies. Measure built output against the hard 1 GB Pages cap and an agreed lower output budget with headroom. Never silently omit originals, transcode masters or hotlink to fit limits.

## Inputs and outputs
Consume the versioned contracts and sanitized fixtures from MIG-01 (MIG-01 creates these). Produce implementation, tests and an evidence report within the ownership boundary. Use fixtures to work independently of production data; never invent production content.

## Acceptance criteria
- [ ] All owned masters and shipped renditions have verified hashes; all observed legacy URLs/references have tested destinations or documented accepted limits; no unresolved references; embedded players pass playback checks. Generated renditions are Astro-processed and limited to actual content/layout needs. Repository and built output sizes are measured against their distinct constraints. If the output cap requires external owned storage, document a decision and get owner agreement before architecture changes.
- [ ] Document inputs, outputs, errors and reproducible verification in the PR.
- [ ] Include evidence against every acceptance criterion and identify remaining blockers.

## Verification contract
Implement and run `python -m unittest discover -s tests/import_media -v` as part of this task. These future commands are acceptance contracts, not commands available in the initial planning scaffold. MIG-07 wires the completed suites into CI; coordinate shared package scripts with MIG-04.

## Handoff
Link the PR and evidence here. Consumers use the committed contracts/artifacts, not another agent's uncommitted working tree. Do not change production DNS as part of any task other than approved MIG-09.
